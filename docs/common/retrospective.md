# 달빛약속 스텝 디버거 - 프로젝트 회고

**프로젝트 기간**: 2026-04-24 ~ 2026-04-27 (4일)
**최종 상태**: MVP 완성 (예제 라이브러리 일부 제외)

---

## 1. 잘된 점

### 1.1 핵심 기능의 완전한 구현

PRD에서 정의한 세 가지 핵심 실행 모드(단계별 실행, 자동 실행, 전체 실행)를 모두 구현했고, 각 모드가 독립적으로 작동한다. 특히:

- **단계별 실행(Step-by-step)**: "다음 단계" 버튼을 누를 때마다 정확히 한 줄씩 실행되며, 각 단계의 변수 상태가 정확하게 추적됨
- **자동 실행(Auto-run)**: 속도 슬라이더로 자유롭게 속도를 조절하며 코드를 자동으로 실행 가능
- **전체 실행(Run All)**: 지연 없이 코드를 전부 실행하고 최종 결과를 즉시 표시

이 세 모드는 사용자가 코드 동작을 이해하는 여정의 서로 다른 단계를 지원한다. 처음부터 세심하게 단계별로 보거나, 패턴을 빠르게 확인하거나, 최종 결과만 빠르게 확인할 수 있다.

### 1.2 달빛약속 런타임과의 완벽한 통합

`@dalbit-yaksok/core` 라이브러리의 `YaksokSession` API를 깊이 있게 이해하고 통합했다:

- `runningCode` 이벤트를 통해 매 단계마다 현재 실행 위치(line, column), 변수 상태(scope), 토큰 정보를 정확하게 캡처
- `pause()` / `resume()` API를 활용한 세밀한 실행 제어
- 자동 실행 시 `executionDelay` 옵션으로 부드러운 애니메이션 제공
- 사용자 입력이 필요한 경우 `stdin` 핸들러를 구현하여 대화형 프로그램 지원

런타임이 던지는 복잡한 데이터 구조를 올바르게 해석하여 UI에 반영하는 데 성공했다.

### 1.3 FSD 아키텍처의 일관된 적용

처음부터 Feature-Sliced Design 원칙을 지키려고 노력했고, 프로젝트 진행 중에도 이를 유지했다:

- 페이지는 조합 전용으로 축소되었고, UI 로직은 `features/debugger/ui/`로 분리됨
- 상태 관리(`debugStore`), 커스텀 훅(`useDebugger`, `useDebuggerSync`)이 명확히 계층화됨
- `entities/`가 비즈니스 로직의 기초를 담당하도록 설계
- 단방향 의존성 규칙을 준수하여, 상위 레이어가 하위만 참조

덕분에 새로운 기능을 추가하거나 버그를 수정할 때 영향 범위가 최소화되었다.

### 1.4 에이전트와의 효율적인 협업

25개의 에이전트 협업 로그를 남기면서, 작업의 추적성과 책임성을 높일 수 있었다:

- 기능 구현, 버그 수정, 리팩토링 등 각 작업 단계별로 에이전트가 수행한 내용과 검증 방법을 기록
- 복잡한 런타임 버그(예: 무한 초기화)를 만날 때마다 그 원인과 해결 과정을 남김
- 에이전트의 산출물을 어떤 방식으로 검증했는지 명시하여, 나중에 같은 문제가 생겼을 때 대응 가능

4일이라는 짧은 기간에도 불구하고 25개의 의미 있는 작업을 완료할 수 있었던 핵심은 에이전트와의 명확한 커뮤니케이션이었다.

### 1.5 안정적인 오류 처리

Error Boundary와 오류 페이지(`/error`)를 구현하여, 예상치 못한 런타임 에러가 발생해도 앱이 완전히 깨지지 않도록 했다:

- React Error Boundary로 컴포넌트 렌더링 에러 캡처
- 별도의 에러 페이지에서 사용자 친화적인 메시지 표시
- 개발 환경에서는 상세한 에러 스택을 확인 가능
- 프로덕션 환경에서는 불필요한 `console.error` 제거 완료

사용자가 잘못된 코드를 실행하더라도 디버거 자체는 안정적으로 유지된다.

### 1.6 명확한 변수 표시

변수 패널이 현재 스코프의 모든 변수를 타입별로 명확하게 표시한다:

- 변수명, 타입, 값이 한눈에 보이는 테이블 형식
- 숫자, 문자열, 불린, 리스트 등 복합 타입을 올바르게 포맷팅
- 각 단계마다 변수 값이 실시간으로 업데이트
- 리스트 같은 복합 타입도 [`1`, `2`, `3`] 형식으로 명확하게 표현

초급 학습자도 변수가 어떻게 변하는지 추적하기 쉬워진다.

## 2. 아쉬웠던 점 및 개선 방안

### 2.1 자동화 테스트의 부재

**현황**: Unit 테스트나 E2E 테스트가 전혀 없다. 모든 검증이 수동으로 이루어졌다.

**문제점**:
- 새로운 기능을 추가할 때마다 기존 기능이 깨지지 않았는지 수동으로 확인해야 함
- 버그 수정 후에도 같은 문제가 다시 생기지 않는다는 보장이 없음
- 4일간 25개의 작업을 하면서 여러 차례 회귀 버그가 발생함 (특히 세션 동기화 버그)

**개선 방안**:
```bash
# Vitest + React Testing Library 도입
pnpm add -D vitest @testing-library/react @testing-library/user-event

# 최소한 다음 시나리오는 테스트 커버리지 필요:
# 1. 단계별 실행이 정확히 한 줄씩 진행되는가?
# 2. 변수 상태가 정확하게 업데이트되는가?
# 3. 실행 중단 → 재개 시 상태가 유지되는가?
# 4. 코드 변경 시 상태가 초기화되는가?
```

### 2.2 설계 문서를 개발 후반에 작성함

**현황**: 아이디에이션, ADR, 아키텍처 문서가 PRD에는 있지만, 개발 진행 중에는 문서를 충분히 업데이트하지 않았다.

**문제점**:
- 개발 중 의사결정(예: 왜 `zustand`를 선택했는가?)이 암묵적으로 이루어짐
- 중간에 구조 변경이 있을 때 문서가 실제 코드와 달라짐
- 다음 개발자가 코드의 의도를 파악하기 어려움

**개선 방안**:
```
개발 전:
1. 시스템 아키텍처 다이어그램 작성
2. 상태 관리 방식 결정 (ADR)
3. 컴포넌트 계층 구조 정의

개발 중:
1. 각 기능마다 설계 결정 기록 (ADR)
2. 예상과 다른 부분은 즉시 문서 수정

개발 후:
1. 최종 아키텍처 문서 확정
```

### 2.3 에이전트 산출물의 검증 프로세스 수동에 의존

**현황**: 에이전트가 코드를 작성한 후, 개발자가 수동으로 코드 리뷰 → 테스트 → 머지를 진행했다.

**문제점**:
- 에이전트가 생성한 코드 중 일부가 타입 에러나 논리 에러를 포함하기도 함
- 검증 과정이 번거로워서 때때로 충분하지 않은 검증으로 진행함
- 같은 실수가 반복될 수 있음

**개선 방안**:
```bash
# 자동화된 검증 파이프라인 구축
1. 에이전트가 PR을 생성하면 자동으로:
   - pnpm tsc (타입 검사)
   - pnpm lint (린트)
   - pnpm test (단위 테스트)
   - pnpm e2e:test (E2E 테스트)

2. 모든 체크가 통과할 때만 머지 가능
3. 에이전트는 CI 결과를 보면서 자동으로 수정 가능
```

### 2.4 복잡한 런타임 버그 해결에 많은 시간 소요

**구체적 사례**:

1. **무한 초기화 버그 (로그 #21)**: 사용자가 에디터에 타이핑할 때마다 상태가 초기화되는 버그
   - 원인: `useEffect`의 의존성 배열에 `code`가 포함되어 있어서, 코드가 변할 때마다 훅이 재실행됨
   - 해결 시간: ~30분 (원인 파악)
   - 배운 점: React hooks의 의존성 관리는 신중해야 함

2. **세션 동기화 버그**: 자동 실행 중에 코드를 변경하면 예상치 못한 동작이 발생
   - 원인: 여러 개의 `useEffect`가 세션 재생성을 서로 다른 조건으로 트리거함
   - 해결 시간: ~45분
   - 배운 점: 상태 관리가 복잡할수록, 상태 변경이 어떤 사이드 이펙트를 일으킬 수 있는지 체계적으로 추적해야 함

**개선 방안**:
- 상태 다이어그램(State Machine)을 설계한 후 구현 (XState 라이브러리 활용)
- 상태 전이가 유효한지 사전에 검증
- 각 상태에서 특정 actions만 허용하도록 구조화

## 3. 시간이 더 있었다면 하고 싶었던 것

### 3.1 브레이크포인트 설정 기능

**범위**: 현재 Out of Scope이지만, 고급 사용자에게는 매우 유용할 기능

**구현 방안**:
- 에디터의 줄 번호 왼쪽에 클릭 가능한 영역 추가
- 클릭하면 해당 줄에 빨간 점 마크 표시
- 코드 실행 시 브레이크포인트 도달하면 자동으로 일시정지
- "조건부 브레이크포인트" 지원 (예: 변수 값이 특정 조건을 만족할 때만 일시정지)

**예상 소요 시간**: ~4시간

### 3.2 이전 단계로 되감기 (Rewind)

**범위**: 현재 단계별 실행은 한 방향(순방향)만 지원하지만, 이전 단계로 돌아가는 기능은 학습에 큰 도움이 될 것

**구현 방안**:
- 모든 단계의 상태를 프레임 배열로 메모리에 유지 (현재도 일부 구현됨)
- "이전 단계" 버튼 추가
- 현재 프레임 인덱스를 감소시키고 UI 업데이트
- 변수 패널, 출력 로그도 해당 프레임 상태로 복원

**예상 소요 시간**: ~2시간 (기본 구조는 이미 존재)

### 3.3 더 많은 예제 코드 라이브러리

**현황**: 예제 페이지는 구현했지만, 예제 코드가 충분하지 않음

**추가하면 좋을 예제들**:
1. **함수 정의 및 호출**: 매개변수 전달, 반환값
2. **중첩 반복문**: 별 모양, 구구단 등
3. **함수형 리스트 처리**: 리스트 순회, 필터링, 매핑
4. **재귀 함수**: 팩토리얼, 피보나치
5. **복합 데이터 타입**: 딕셔너리/맵 구조 (달빛약속 지원 여부 확인 필요)
6. **실전 예제**: 성적 계산, 온도 변환, 소수 판별 등

**예상 소요 시간**: ~3시간 (예제 코드 작성 + 테스트)

### 3.4 모바일 반응형 대응

**현황**: 데스크톱 기준으로만 최적화됨

**구현 방안**:
- 모바일에서는 에디터와 패널을 상하 배치 (현재는 좌우 배치)
- 패널을 탭 방식으로 전환 (변수 패널 / 출력 로그를 tab으로 선택)
- 터치 친화적인 버튼 크기 (최소 48x48px)
- 메타 뷰포트 설정: `<meta name="viewport" content="width=device-width, initial-scale=1.0">`

**예상 소요 시간**: ~3시간

### 3.5 Vercel/Netlify 배포

**현황**: 로컬에서만 실행 가능 (`pnpm dev`)

**구현 방안**:
```bash
# Vercel 배포 (React/Vite 친화적)
npm i -g vercel
vercel login
vercel

# 또는 GitHub Actions로 자동 배포
- Vite 빌드 (npm run build)
- dist/ 폴더를 GitHub Pages에 배포
```

**이점**:
- 실제 사용자가 URL을 공유받고 즉시 사용 가능
- 달빛약속 공식 문서나 교육 기관에서 링크 가능
- 프로젝트의 가시성 증가

**예상 소요 시간**: ~1시간

### 3.6 달빛약속 런타임의 더 깊은 활용

**현황**: 현재는 기본적인 runtime execution만 사용

**가능한 고급 활용**:
1. **AST 시각화**: 파서가 생성한 Abstract Syntax Tree를 시각적으로 표시
2. **바이트코드 뷰**: 달빛약속이 컴파일한 중간 바이트코드 표시
3. **메모리 프로파일링**: 각 단계에서 메모리 사용량 표시
4. **실행 시간 분석**: 어느 부분이 오래 걸리는지 분석

**예상 소요 시간**: ~8시간 (달빛약속 내부 구조 학습 포함)

## 4. 주요 배운 점

### 4.1 에이전트 협업의 구조화

에이전트와 효율적으로 협업하려면:
- **명확한 작업 스코프 정의**: "이 파일의 이 부분을 이렇게 리팩토링해줘" (vs "리팩토링 해줘")
- **검증 방법 사전 합의**: "완료 후 pnpm lint && pnpm tsc로 검증"
- **산출물 기록**: 뭐가 바뀌었는지 에이전트가 자세히 설명하도록 유도
- **실패 사례 처리**: 에이전트가 실수했을 때 어떤 부분이 잘못됐는지 정확히 지적

### 4.2 상태 관리의 복잡성

zustand + immer를 사용했지만, 상태가 점점 복잡해지면서 여러 버그가 발생했다:
- 상태 전이의 흐름이 명시적이지 않아서 버그 발견이 어려움
- 여러 곳에서 상태를 동시에 수정하면서 race condition 발생

**배운 교훈**: 상태 관리가 복잡하면 State Machine(XState, Redux등) 같은 프레임워크를 처음부터 고려해야 함.

### 4.3 RuntimeError의 처리 어려움

달빛약속 런타임이 던지는 `MachineReadableError`의 구조를 완전히 파악하는 데 시간이 걸렸다:
- 에러 타입, 메시지, 위치(line, column) 정보가 모두 다른 필드에 있음
- 한국어 에러 메시지는 도움이 되지만, 때때로 모호함

**배운 교훈**: 외부 라이브러리를 통합할 때는 에러 처리부터 먼저 이해하고 설계해야 함.

### 4.4 FSD 아키텍처의 가치

FSD를 지킨 덕분에:
- 새로운 기능 추가할 때 어디에 배치할지 명확함
- 리팩토링 후에도 import 경로가 일관되게 유지됨
- 같은 레이어의 다른 슬라이스에 영향을 주지 않음

처음에는 "이렇게까지 엄격해야 하나?" 싶었지만, 4일간 25개 작업을 하면서 FSD의 가치가 명확히 드러났다.

## 5. 결론

달빛약속 스텝 디버거 프로젝트는 **핵심 목표를 달성한 성공적인 MVP**다.

**성과**:
- 사용자가 코드를 한 줄씩 실행하면서 변수 변화를 관찰할 수 있는 시스템 완성
- 세 가지 실행 모드가 모두 안정적으로 작동

- FSD 아키텍처 일관성 유지

- 자동화 테스트 도입으로 버그 회귀 방지
